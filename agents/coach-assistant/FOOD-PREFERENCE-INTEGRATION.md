# Dietary profile preference

Prepared product capability with execution limited to isolated integration until AG1 installs/adopts the schema. This is a new real profile field, not an existing product field or thread memory. No production migration, route, UI or database execution in this slice.

AG1-approved storage: client_profiles.food_preferences, exact JSON `{version:1,dietPattern:null|'omnivore'|'vegetarian'|'vegan'|'pescatarian'}`. Null means not declared; never default/infer omnivore. Shared browser-light contract lib/food/preferences.ts; shared SQL writer lib/food/preference-service.ts. Existing notes, allergies, goals, professional plans and workout_preferences are not modified.

Compose createFoodPreferenceService(database) with executeFoodPreferenceAction(authenticatedActor,raw,authorizedRepository,service,signal) in the existing gated handler. Operations diet.read/propose/apply/receipt use version coach-assistant.v2, conversationId, turnId and profileId. IMPORTANT: profileId denotes the authenticated subject/user ID, not client_profiles.id. Proposal adds resourceVersion and after (full exact v1 preference JSON). Apply requires proposalId/hash/actionId/resourceVersion/reviewed:true. Receipt recovery uses the same actionId.

Current client/self/org authorization is held with profile/membership share locks; canonical client profile is then update-locked on the same transaction. Five-minute proposal binds before/after, scope, resource version, conversation and hash. Apply checks revision and canonical before, reauthorizes and invokes the same transaction writer, then commits receipt and audit together. Foreign IDs, stale versions, expired proposals and action reuse with different bindings fail. Original lost-response recovery is by durable receipt, not a new action. The SQL access is explicitly parameterized against the agreed future column; no Drizzle cast pretends that the current schema already contains it.

Missing column/table SQLSTATE 42703/42P01 maps to not_connected; no storage fallback. AG1's pending DDL: private.coach_food_preference_versions(subject_id PK = client_profiles.user_id, revision >=0). Retain tombstones, invalidate old and new owner on user_id changes, skip null owners, backfill and increment on ordinary changes and delete/recreate. Same private action ledger; allow action food.preference.update. No new ledger. AG1 pending files outside repository: food-profile-column.sql.pending and coach-food-preference-actions.sql.pending. Not executed by AG3.

Refresh result requests profile refetch and discardDerivedContext:true. createFoodPreferenceTurn wraps the already composed Workout/memory repository OUTSIDE those brokers; its personalContext reads fresh preference/version without replacing training preferences or memory. Route must pass its filterHistory through runConversation.filterMemoryHistory (compose after any memory filter). It conservatively keeps literal user history as historical data and discards assistant/summary-derived history each turn, avoiding stale preference authority even across null→value→null. Conversation returns a separate foodPreference field and sends its current declared value/version to the model as profile data, not an allergy, diagnosis or instruction. On a failed conversation it is removed. No route is enabled here.

Validation: eight new tests (writer2, transaction5, context1) plus 25 existing conversation/context-budget tests =33 passing; scoped TypeScript and lint pass. Transactions use injected SQL doubles, including rollback and a simulated committed response loss followed by receipt recovery. Not real PostgreSQL/RLS/HTTP or provider evaluation.
