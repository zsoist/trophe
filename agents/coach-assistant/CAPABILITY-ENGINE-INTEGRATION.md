# Model-selected read/proposal capabilities

Server opt-in runConversation option capabilityRegistry=createCoachCapabilityRegistry({food,preference}). Services are the existing concrete factories, not model implementations. No handler/route/UI activation is included. The existing synthetic/provider-isolation gate remains unchanged: no arbitrary injected transport with authorized production records. Tests use synthetic identity/record context and the concrete transaction services backed by SQL doubles.

Flow: initial current authorization → existing medical boundary → optional fresh personalContext (one counted logical read, existing outer memory/diet filter) → one structured model capability selection → canonical read and optional canonical proposal → existing generateOpenConversation continuation. No regex parses tool intent. Food profile capabilities are available globally, including Workout; the typed model choice supplies intent. Quantity capabilities require the explicit selected meal UUID, then server ownership authorization; no model-invented ID or assumed latest meal. No selection gives select_food_entry_for_quantity and no service call. Missing capabilities use none/not_connected; an unlisted tool or extra identity/apply argument is invalid_output.

Only food.quantity.read/propose and food.preference.read/propose exist. Versions and subject/org identities come from the server read/context. Every service operation reauthorizes in its transaction; registry additionally checks current context before/after and binds returned objects to exact resource/version/after. Apply and receipt are intentionally absent from this model registry; UI confirmation still calls canonical apply with reauth/CAS/idempotency. Returned capabilityResult.applied is always false. The canonical proposal result is separate from prose and contains real service proposal ID/hash/before/after. No receipt is fabricated.

At most two provider invocations, maxAttempts1 each and no repair/retry; the second is the existing open generator with existing prose/receipt-claim guards. No aggregate record reads in this explicit capability branch. A proposal consumes two counted service reads plus optional fresh personalContext, at most three logical reads; the guard remains four. Both prompts enforce 7500 UTF8 bytes including schema/system; output cap2000 each and usage validated/accumulated. Existing total45s deadline and cancellation govern the whole turn. Tool results/history are DATA, never permission or prompt instructions. Non-capability conversation behavior stays on its existing branch when no registry is configured.
