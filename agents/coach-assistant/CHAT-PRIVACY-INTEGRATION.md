# Coach chat privacy integration contract

`createCoachChatPrivacy(database).export(scope, signal)` is a self-service supplement to the existing public privacy export. The future route must construct `scope` from the current server session and must return the result status unchanged. It must not accept actor, subject, organization, or role values from the request body.

The supplement exports private thread and action metadata, memory bindings, attachment metadata, and Photo Food observations. Chat message text remains owned by the existing `public.agent_conversation` export and is referenced only by `turnBindings.content_id`. A `partial` result names every missing optional collection and every truncated collection; `not_connected`, `forbidden`, and `cancelled` are terminal results rather than successful exports.

Before deleting `public.profiles`, the erasure route must call `eraseBeforeProfileDelete(userId, attachmentErasurePort, signal)` with a privileged, reviewed private Storage erasure port. The port receives the immutable actor, subject, organization, conversation, bucket, and object path from the inventory and must idempotently remove and attest the exact bucket and path. This covers rows where the erased identity is either actor or subject; it does not impersonate the original actor through the ordinary attachment service. The route may proceed to profile deletion only when the result is exactly `{status: 'complete', remaining: 0}`. `pending`, `failed`, or an exception must leave the profile intact and keep the erasure request retryable. The helper marks metadata removed only after the port attests physical removal, rechecks the full inventory, and only then removes Photo Food observations and removed attachment metadata. Inventories over 1,000 objects are processed in resumable batches.

This module does not delete the profile, authentication identity, public export data, or public cascade-owned rows. It does not prove full account erasure by foreign keys. AG1 must add `private.coach_attachment_uploads` and its Storage bucket to the central erasure coverage inventory when wiring the gated route, and the route must fail closed if the private schema or removal port is unavailable. The route also needs a durable erasure gate, checked by every private-object writer, to prevent a new upload between the final zero inventory and profile deletion. Feature flags remain off until native database and Storage integration tests establish that an interrupted run resumes without orphaning objects, permitting a race, or reporting success early.
